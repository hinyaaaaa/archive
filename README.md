# Project Archive

個人開発プロジェクトの保存庫。主目的は完成品の公開ではなく、各プロジェクトがどのように分岐し、再設計され、次のプロジェクトへ接続されていったかを記録すること。特に、旧プロジェクトのコードが失われている場合でも、残存する `HANDOFF_*.md`、`REBUILD_PROMPT_*.md`、Git履歴、アーカイブ時点のファイル構成から開発思想と技術的変遷を追えるようにする。

## 開発系譜

```text
StratoNote
├── VocaDesk
│   └── VocaAir
└── Altair v1.8
    └── Altair v2.3
        └── Flowly
            └── TaskEngine
                └── TaskNOVA
                    └── Temper

Ankel v1
└── Ankel v2

OshiCamera
```

StratoNoteが最初期の基盤プロジェクトで、そこから「学習・語彙系」と「タスク管理系」に分岐した。タスク管理側では Altair の自動割り当て思想が Flowly、TaskEngine、TaskNOVA を経て再構成され、現在の Temper へ接続している。一方 Ankel は系譜上独立したローカルAI・検索基盤で、OshiCameraも別系統の独立プロジェクト。

## 1. StratoNote

最初期の基盤プロジェクト。現在のコードは残っていないが、後続プロジェクトの系譜上はここが起点となる。StratoNoteから大きく二方向へ分岐し、ひとつは語彙・学習系のVocaDesk→VocaAir、もうひとつはタスク管理系のAltair→Flowly→TaskEngine→TaskNOVA→Temperとなった。したがってStratoNoteは単一アプリの完成形というより、その後の開発テーマを生み出した原点として位置づけられる。

## 2. VocaDesk → VocaAir

StratoNoteから分岐した語彙・学習系統。VocaDeskについては現在の公開リポジトリを確認できないため細部の履歴は不明だが、系譜としては「知識・語彙を扱うツール」という方向へ分化したことが確認できる。VocaAirはこの系統の後継にあたり、GitHub上では2026-06-14からコミットを確認でき、2026年8月にも継続的な更新が行われている。Altair系とは異なりタスク自動割り当てを主軸とせず、別方向の問題設定を追ったプロジェクト群として残る。

## 3. Altair v1.8

Altair初期世代。現存する `HANDOFF_Altair.md` の履歴から、v1.8ではタイマー、暗記カード、スキルツリー、テスト成績、実績バッジなど、複数の機能を一つのアプリに集約していたことが確認できる。ただしこれらは後の世代で削除され、タスク管理そのものへ大きく焦点が移る。ここは「学習・生活支援を多機能にまとめる段階」から「タスク計画そのものを自動化する段階」へ移る前段と考えられる。

## 4. Altair v2.0〜v3.x

Altairの中心的転換点。v2.0でタスク自動割り当て、週次タスク、壁紙などが導入され、単なるタスクリストから「今日何をやるかを自動決定するシステム」へ変化した。v2.1ではファイル分割、GitHub Pages対応、iOS PWAのsafe-area問題修正、`window.confirm()`依存の排除など、UIだけでなく配布・運用環境を意識した設計へ移行。v2.2では平日・休日のキャパシティ分離、祝日、残りキャパシティ、全完了と目標達成の区別、完了済みonceタスクの翌日自動削除、`doneDate`を導入。v2.3では再生成を「完了済み保持＋未完了のみ再配置」に変更し、キャパシティ変更時も同じ考え方でリバランスする設計に変更。v2.4では週次タスクの負荷を正しくキャパシティへ算入するため `internalUsed` を導入。v2.5では保存キーをバージョン非依存の `altair_data` に統一し、旧キーからの自動マイグレーションを追加。v2.7では負荷上限を0.5〜5へ整理し、負荷4以上の重いタスクを原則1日1つに制限。v2.8ではスナップショット外タスクを「今日達成」に追加できる `extraDoneToday` と、最速完了日シミュレーション `simulateEarliestCompletion()` を導入。v2.9では一覧上のチェック操作と当日負荷を統合し、エクスポート名も固定。v3.0ではキャパシティ達成後でも期限超過・本日期限・明日期限の緊急タスクを表示する仕組みを追加し、今日画面の挙動を整理した。結果としてAltairは「タスクを保存するアプリ」ではなく、「期限・負荷・曜日・完了状況から今日の行動を決定するスケジューリングエンジン」を中心に据えた設計へ収束した。

## 5. Flowly

Altair系からTaskEngineへ移行する中間世代。現存する詳細なHANDOFFは確認できないため具体的な機能履歴は限定的だが、系譜上はAltairのタスク割り当て思想を引き継ぎつつ、後のTaskEngine／TaskNOVAで採用される「タスク管理UIと視覚表現を分離する」方向への過渡期に位置する。README上では独立系統として残す一方、詳細は「Altair→TaskEngine間の中間世代」として扱う。

## 6. TaskEngine

Altair系のアーキテクチャ刷新世代。特に重要なのは、以前の「1MB超の巨大な `index.html`」を分割した点。従来は約910KBのテクスチャデータを含む単一HTMLを初回読み込み時に全て取得・解析する必要があったが、TaskEngineでは `index.html` 約16KB、`css/app.css` 約44KB、`js/app.js` 約76KB、`js/solar-system.js` 約28KB、`js/textures-data.json` 約892KBへ分離。初回表示に必要なファイルと、「今日」タブを開いた時だけ必要なThree.js関連資産を分離し、ブラウザのHTTPキャッシュをファイル単位で効かせる構成へ変更した。さらにThree.jsを非圧縮約1.27MBからminify約670KBへ変更、Google Fontsの利用ウェイト削減、`preload`・`preconnect`導入など、機能追加よりもロード性能・キャッシュ効率を優先した。この世代でタスク管理システムが「ロジックを動かすHTML」から「複数モジュールで構成されたWebアプリ」へ明確に変化した。

## 7. TaskNOVA

TaskEngineをさらに視覚・操作面から再設計した世代。最大の変更は「タスクタブ＝リスト」という前提を捨て、タスクそのものを3D空間上の浮遊天体として表現したこと。新規の `js/task-field.js` ではタスクIDのハッシュから決定的な球面座標を生成し、緩やかなドリフトを加えて配置。週次タスクはリング付き、締切が近いタスクほど中心に近く、負荷が大きいほど天体を大きくすることで、タスク属性を空間的表現へ変換した。天体選択時にはSVGのリーダーラインとHUDカードを表示し、「達成」「編集」をその場で操作できるようにした。内部ロジックでも `getPoolTasks()` によってキャパシティで絞らない「全未完了タスク集合」を取得し、`completePoolTask()` を共通処理として整理。旧リストUI由来の関数やCSSを大量に削除し、TaskEngine時代のタスク管理ロジックを新しい視覚モデルへ接続した。またiOS Safari向けに `touchend` と合成 `mouseup` による二重発火を800msガードで抑制、safe-area依存の下部余白を修正、DOM差し替え後のWebGLキャンバス再構築漏れを修正、`mousemove` / `mouseup` のイベントリスナー累積も修正。つまりTaskNOVAは見た目だけのリニューアルではなく、DOM再描画とWebGL状態管理の矛盾を整理した大規模リファクタリングでもある。

## 8. Temper

TaskEngine→TaskNOVA系譜の現行世代。GitHub上では2026-09-12から開発履歴を確認でき、2026-09-20時点まで短期間に連続更新されている。初期段階では天候・空・HUD的UIなどの視覚的試行を重ね、その後TaskEngine系のタスク管理思想を取り込みながら、UI、PWA、週間タスク、履歴、並び替え、当日状態などを整理。v1.6.0では「全タスク完了目安」の算出を、単純な残タスク×固定時間ではなく、日ごとの容量と週間負荷を考慮した日付ベースの推定へ変更。またiOS/PWA環境で位置情報取得が停止して天候取得全体がハングする問題に対し、約8秒のタイムアウトとGPS取得失敗時のフォールバックを追加。さらにバージョン表示など細部の状態管理も整備された。現在のTemperは、Altair以来の「今日の負荷をどう配分するか」という問題を、TaskEngineの性能設計、TaskNOVAの空間UI、PWA/iOS対応を踏まえて再整理した世代として位置づけられる。

## 9. Ankel v1

タスク系とは独立して進められたローカルAI基盤。目的はScrapboxからエクスポートした知識をブラウザへ取り込み、外部APIへ送信せず、ローカル完結でRAG型の検索・対話を行うこと。IndexedDBへデータを保存し、Scrapbox JSONをインポート、Embeddingを生成し、Wllama / Transformers.js / WebLLM系のローカル推論技術を組み合わせる構想だった。GitHub Pagesで配布できる静的Webアプリとして設計され、初期版ではWllamaとマルチスレッド推論のためのSharedArrayBuffer対応、`coi-serviceworker.js`、WebWorkerによるAI処理を採用。標準・文章作成・論理処理など用途別の小型モデルを切り替える設計も含まれていた。思想としては「過去資料をブラウザ内へ持ち込み、その場で質問できる個人用知識基盤」。

## 10. Ankel v2

Ankel v1から大きく方向転換し、「AIチャットアプリ」より「検索エンジン」を中核に据えた世代。現行アーカイブでは `client/index.html`、`data/pages.json` / `chunks.json` / `vectors.json` / `qa_index.json` / `qa_vectors.json` / `chunk_vectors.json`、`server/server.js` 等に分離され、Node.jsサーバー上でScrapboxデータを横断検索する。APIは `/api/search`、`/api/page`、`/api/import`、`/api/related` を提供。検索パイプラインは `parseQuery()` → BM25 → 共起語解析 → 各指標の統合 → ベクトル補助という多段構成で、年度展開、同義語、アイコンID、2/3-gram、`allSegments`、PageRank、年度重み、意図分類、近接性、本文先頭密度、共起語、ベクトル検索、QAベクトル、チャンクベクトルを併用する。概念上の最終スコアは `(min(bm25,40)*15*lenPenalty + pr*30 + prox + vecScore + frontBonus) * tagMult * intentBonus * yWeight`。つまり「完全一致するキーワードを探す」から「曖昧な問い合わせでも文脈と構造から目的の資料へ到達する」方向へ進化した。さらに再構築案ではWebLLM + WebGPUへの移行、Wllama・`ai-worker.js`・`coi-serviceworker.js` の廃止、IndexedDB検索とローカルLLMの統合が計画されており、Ankel v2は検索基盤とローカルAIを一体化する方向へ進んでいた。

## 11. OshiCamera

タスク系ともAnkel系とも独立した別系統。GitHub上では2026年7月から継続的な更新を確認でき、短期間に多数のコミットを行いながらキャラクター、影、配置、UI等を反復的に調整している。2026-07-29頃にはキャラクターデータへの属性追加、テストディレクトリ整理などが行われ、2026-09-18にはUI刷新用ADRの整理も確認できる。開発方法としては、比較的大きな設計変更を一気に入れるより、視覚要素・データ定義・配置・UI部品を細かいコミット単位で反復するタイプのプロジェクトとして特徴づけられる。

## 技術的な大きな転換

このアーカイブ全体を見ると、開発は大きく「機能追加 → 自動化 → アーキテクチャ分割 → 視覚化 → 再抽象化」という流れを取っている。初期のStratoNote/Altairでは複数機能を一つへ集約する傾向が強かったが、Altair後半では「今日やるべきことの自動決定」という単一の問題へ集中。TaskEngineではコード・データ・描画資産を分離し、ブラウザのロードモデルそのものを改善。TaskNOVAではタスク情報をUI上の意味に変換し、負荷・締切・週次性を空間配置へ変換。Temperではそこからさらに日付推定、PWA、iOS、週間状態など実運用上の問題へ戻り、機能とUXの統合を進めている。Ankelでは逆にUIより検索アルゴリズムへ重心が移り、BM25、PageRank、共起、意図分類、ベクトルなど複数の検索信号を統合する方向へ進んだ。

## プロジェクトごとの設計思想

**StratoNote:** 最初の実験場・後続系統の起点。
**VocaDesk / VocaAir:** 語彙・学習を扱うための独立系統。
**Altair:** 「今日何をするか」を自動決定するタスク計画。
**Flowly:** Altairから後続タスク基盤へ移る中間世代。
**TaskEngine:** タスクエンジンの内部構造・ロード性能・キャッシュ設計を刷新。
**TaskNOVA:** タスクを情報一覧ではなく3D空間上のオブジェクトとして再解釈。
**Temper:** TaskEngine/TaskNOVA系を実運用寄りへ再整理し、PWA・iOS・日付推定などを統合。
**Ankel v1:** ローカルAI＋Scrapbox＋RAG。
**Ankel v2:** RAGチャットから検索エンジン中心へ再設計。
**OshiCamera:** 独立系統。ビジュアルとデータ構造を細かく反復改善。

## アーカイブ上の注意

このリポジトリへの登録日と、元プロジェクトの開発時期は区別する。`archive` に2026-09-20前後で多数の `Add files via upload` / `Delete ...` コミットが存在するが、これは旧プロジェクトを後から整理・登録した履歴であり、元プロジェクトの開発期間そのものを示さない。したがって年代を確定できる場合は元リポジトリのGit履歴を優先し、Git履歴がない場合はHANDOFF等の内部資料から確認できる情報だけを記録する。また、内部バージョン文字列・サンプルデータの日付・コード中のテスト用日時は、実際の開発開始日として扱わない。

## 保存方針

旧プロジェクトのコードが現存しなくても、`HANDOFF.md`、`REBUILD_PROMPT.md`、設計資料、バージョン履歴などの残存文書から「何を作ったか」「何を捨てたか」「なぜ構造を変更したか」を可能な限り復元する。完成版だけでなく、削除された機能、旧アーキテクチャ、移行理由、既知の制約も履歴情報として保存する。このアーカイブは成果物一覧ではなく、開発思想そのものを保存するための記録である。
